# k8s.txt 方案评审与补充

> 本文只做评审，不含实现代码。所有"现状"结论都跟仓库当前代码核对过，附了文件与位置，便于你自己翻一遍确认。

## 0. 总体判断

方案本身的骨架是对的：任务域独立成 app、API 只创建任务不执行、状态机 + 阶段 + 事件 + 审计、制品走自有 OSS 且目标节点不持有凭据、Local-only 且目标节点不装 agent。这几条边界划得很清楚，尤其是"不把长任务塞进 Web 请求线程"和"目标节点不碰 OSS"，这两条能省掉后面一大堆麻烦。

需要修正的地方集中在两类：

1. **对现状的假设有偏差**（Channels 的实际可用性、OSS 客户端的实际存在性、权限码的实际体系）。这几处如果按方案字面理解去排工期，会低估工作量。
2. **执行环境的空白**（Windows 开发机 + SQLite + 密码怎么交给 Ansible）。这三条不是细节，它们决定 Phase 1 能不能落地和能不能测试。

下面按"必须修正"、"建议补充"、"顺序建议"、"待你拍板"四段写。

---

## 1. 必须修正：方案描述与仓库现状不符

### 1.1 Channels 已启用，但当前配置撑不起"Worker 推日志到前端"

方案第 2 章和 7.3 节把 WebSocket 实时日志当成现成能力。实际情况：

- `backend/backend/settings.py` 的 `CHANNEL_LAYERS` 用的是 `channels.layers.InMemoryChannelLayer`。
- 部署 Worker 按方案 3.1 是**独立进程**（`manage.py run_deploy_worker`）。InMemory 层只在一个进程内有效，Worker 发布的事件到不了 Web 进程。多 Web worker 进程之间同样不通。
- 现有两个 consumer（`backend/k8s_platform/consumers.py`，Pod exec 和 Pod 日志）是"浏览器 ↔ 单个 consumer 进程"的直连模型，不需要跨进程投递，所以 InMemory 一直没暴露问题。

结论：**方案 7.3 的实时日志协议，要么先不上 WebSocket，要么必须先引入 `channels_redis`。**

建议：Phase 1 只做 `GET /deployments/<id>/events/?after=<seq>` 的 HTTP 轮询（方案 6.3 里本来就有这个接口，事件表也已经有 seq，这正是为轮询准备的），WebSocket 放到 Phase 2 跟 Redis 一起上。轮询对"部署进度"这个场景完全够用，而且断线续传、去重、重放全都是免费的。

另外前端 `apiStream`（`front/src/api.ts` 约 154 行）是 **fetch + 手工解析 SSE**，不是 `EventSource`。它需要服务端一直保持响应不结束，用 Django 跑长连接会占住一个请求处理单元，WSGI 部署下尤其明显。这也是"先轮询"的另一个理由。

### 1.2 `storage.oss` 只是"被保存下来的设置"，后端没有任何 OSS 客户端

方案 15.2 的写法是"当前已有 `storage.oss`，建议扩展同一个平台级设置"，容易读成"可以复用现有实现"。实际核对：

- 前端 `front/src/views/workbench/PlatformSettingsPanel.vue` 有 OSS 表单，保存到 `SystemSetting`，`key = storage.oss`，值走 `EncryptedJSONField`（`backend/ops/models.py` 约 399 行）。这一层是齐的。
- **后端没有任何代码去消费 `storage.oss`**：`backend/ops/services/` 下没有 OSS/对象存储模块，全仓库搜不到 OSS SDK 调用。
- `backend/requirements.txt` 里**没有** `boto3`、`oss2`、`pynacl`。已有的网络类依赖是 `requests` 和 `paramiko`（`paramiko` 只用在 `ops/services/system_tools.py` 做 SSH 登录校验）。

结论：方案第 15 章的"制品仓库"整体是**从零新建**，不是复用。请把工期按"新增一个 app + 存储适配器 + 签名校验 + 下载器 + 缓存"来估。

还有一个具体的坑：方案 15.2 写"编辑时使用 `********` 表示保持原值"。**现在没有这个逻辑**——前端保存 OSS 配置时是把 `access_key_secret` 原样回传的（`PlatformSettingsPanel.vue` 约 712-720 行的 payload 构造）。如果不先做这个占位符协议就上 reveal 功能，会出现"用户点开编辑、直接保存，密钥被替换成八个星号"的事故。要做就前后端一起做（后端识别占位符则保留原值，前端明确提示），别只做一半。

### 1.3 权限码的"页面"和"操作"被混在一层，且 `page.k8s.deploy.view` 目前没有操作码

现有体系（`backend/ops/permission_catalog.py` 的 `action_code`）是两段式：

- 页面码固定 `.view` 结尾，例如 `page.settings.view`、`page.k8s.clusters.view`；
- 操作码 = 页面码去掉 `.view` 再接动作名，例如 `page.settings.reveal`、`page.k8s.clusters.create`。

方案 15.3 提的那一批 `page.settings.oss.view`、`page.settings.oss.update`、`page.settings.oss.reveal` 把两层混在一起了。而且 OSS 配置卡片就在 `/settings` 页面里（前端没有单独的 OSS 路由），再造一个 `page.settings.oss.view` 页面码，`page_code_for_path` 按路径匹配永远匹配不到它，等于死码。

建议改成：**复用 `page.settings.view` 页面，新增操作码**，例如 `page.settings.artifact_sync`、`page.settings.artifact_prune`；`reveal` 直接复用已存在的 `page.settings.reveal`（0033 号迁移里已经建了）。新增操作码要补 `PermissionMenuAction` 记录（参照 `ops/migrations/0054_notification_test_permissions.py` 的写法：找到页面节点 → 建 action → 给既有策略回填规则）。

同样的问题在部署接口上更严重：

- `page.k8s.deploy.view` 是 `ops/migrations/0070_k8s_cluster_deploy_page.py` 建的，**只建了页面节点，没有建任何 `PermissionMenuAction`**，也就是这个页面目前只有"能不能进"，没有任何操作权限。
- 方案 6.3 的 `POST /deployments/`、`/retry/`、`/cancel/`、`/cleanup/`、`/adopt/` 都是写操作，动作码会去查 `page.k8s.deploy.create` / `.retry` / `.cancel` / `.cleanup` / `.adopt`。**这些码现在不存在，非管理员一律 403。**
- 所以 0070 那个迁移需要**再补一次**：给页面加 actions，并给既有策略回填规则。

### 1.4 每新增一批权限码，既有角色默认是"拒绝"

这条最容易踩，单独列出来。`ops/migrations/0070_k8s_cluster_deploy_page.py` 的回填逻辑是：策略里已经有 `'*'` 就给 `allow`，否则一律 `deny`。也就是说：

> 功能上线了，但除了超管和权限策略里显式授过权的账号，其他人全都 403。

这不是 bug，是既有设计（安全默认）。但方案里完全没提，请在第 8.1 节的"平台侧准备"里补一条：**每次新增权限码，都要说明需要管理员去权限策略里重新勾选**，并在上线清单里列出账号范围。否则测试同学会以为是功能坏了。

### 1.5 新 API 前缀需要在权限别名表里登记，否则直接 403

`backend/ops/permissions.py` 里 `RoleBasedPermission.has_permission` 的逻辑是：拿不到 `page_code` 就 `return False`（不是放过）。

新前缀 `/k8s/deployments` 现在既不在 `API_PAGE_ALIASES` 里，也没有对应的菜单节点 path/alias，`page_code_for_path` 会返回空 → **所有非管理员 403**。方案要在落地清单里明确：每个新前缀都要在 `API_PAGE_ALIASES`（`ops/permissions.py` 开头那张表）登记，或者建带 path/aliases 的菜单节点。这和 1.3 是同一类问题的两个面。

### 1.6 `exec_mode` 没有"历史数据"需要兼容

方案 6.1 写"建议数据库保留字段以兼容历史数据，但 Choice 只允许 `local`"。实际情况：

- 后端**从来没有过** `exec_mode` 字段。
- 前端的"执行模式"（本地/Agent）字段刚刚已经按你的要求**整个删掉了**（类型、选项表、表单项、确认页汇总全部清空），全仓库搜 `execMode` 无残留。

所以没有历史数据可兼容。建议**连字段都不要建**——只保留 local 就不需要用一个字段表达"只有一个取值"。真要在请求体里出现，直接忽略即可。同理方案 3.1 那段"Local-only 执行模式"的说明保留在文档里没问题，但不必落到模型上。

### 1.7 机器模型没有私钥/密钥字段

方案 6.4、8.2、9.1 反复提到"密码/密钥有效"。当前 `backend/k8s_machine/models.py` 只有：

- `encrypted_password`（SM4 密文）
- `password_rotated_at`

**没有**私钥、密钥口令、`ssh_key` 之类的字段。方案里"密钥认证"这条线目前没有落点。要么本阶段明确"只支持密码认证"，要么把新字段和对应的 SSRF/校验一起列进模型改造清单。这属于模型缺口，不是实现细节。

### 1.8 创建请求的参数名前后不一致，`kubeasz_version` 不该由前端传

方案 6.3 的示例请求体用了 `kubeasz_version`，而现有 `POST /k8s/clusters/deploy/` 收的是 `kube_version`（`backend/k8s_cluster/views.py` 约 188 行），前端表单里则是 `k8sVersion` + 本地推导的 `kubeaszVersion`（`deploy/types/deploy.ts` 的 `kubeaszVersionOf`）。

建议统一成 `k8s_version` + `kubeasz_version`，并且**`kubeasz_version` 不入参**：方案 5.1 自己已经写了"禁止客户端自行传入不匹配版本"，但 6.3 的示例又把它传进来了，自相矛盾。让后端按版本映射表推导，前端只传 `k8s_version`，这样版本对应关系只有一个真相来源。

### 1.9 `K8sCluster.status` 与任务状态的一致性规则没写

方案 6.1 说"`status=deploying` 可保留兼容，但状态真相以部署任务为准"，这等于留了一个双写口子。必须把规则写死，否则会出现"集群页显示部署中、任务页显示 failed"这种互相打架的状态。建议：

- `K8sCluster` 上的部署相关字段是**只读投影**，由任务状态机在**同一个事务里**更新，其它地方一律不许写；
- 集群列表页只读投影，不做任务表 join（现有列表接口是单表 + `Case/When` 排序，保持这个形状最省事）；
- 明确 `K8sCluster.STATUSES` 里要不要新增 `failed` 档。现在只有 available/configured/deploying/unconfigured/unavailable/disabled，任务失败后集群该显示什么需要一个明确答案。

顺带：方案列的 `deployment_id` 和 `last_deployment_id` 是冗余的两个字段，留一个 FK（当前活动任务）就够。

### 1.10 部署成功后漏写健康检查记录

方案 6.4 的第 11 步只写了"加密保存 kubeconfig、更新 `K8sCluster` 状态"。但集群列表页的"最近检测"列读的是 `K8sClusterHealthCheck`（本次刚做的那个页面就是走这张表）。部署成功后如果不补一条 health check，新集群的"最近检测"会一直是空的，看起来像没连上。请在第 11 步里补上。

## 2. 建议补充：方案现在的空白

### 2.1 SSH 密码怎么交给 Ansible —— 这是目前最大的安全空白

方案第 9 章反复强调"密码不写日志、不进命令行、只在内存用"，但**没写具体怎么让 Ansible 拿到密码**。kubeasz 的 `hosts` 支持 `ansible_ssh_pass=`，那是最常见的做法，也是最危险的——**明文落盘在 `clusters/<slug>/hosts` 里**，而这个文件正好是方案 15.8 要计算哈希并允许前端查看的对象。

必须补一条明确决策，三选一：

1. 密码只在 worker 内存中一次性转成**临时 SSH 私钥**（或临时 ssh-agent），`hosts` 里只能出现 `ansible_ssh_private_key_file`；临时文件 `0600`，`finally` 里删除。
2. 用密码但走 `sshpass` + 受限参数文件，且**渲染出的 `hosts` 必须做敏感字段扫描**，命中 `ansible_ssh_pass` 就拒绝执行。
3. 本阶段只支持已预置密钥的节点，向导里明确提示。

无论选哪个，都要在配置生成的静态检查里加一条：**渲染结果不允许出现任何 `*_pass`、`ansible_password`**。方案 5.3 第 4 条只写了"敏感字段扫描"，没有点名这个具体模式，建议写死。

### 2.2 Windows 开发机跑不了 Local Worker —— 这是能不能落地的问题

这是当前工作目录的实际约束：仓库在 Windows 上，而 `ezctl` 是 Bash + Ansible，必须有 Linux 平台服务器。方案第 14 章第一句提到了这点，但没给出应对方式。建议明确两条：

1. **Phase 1 就要定下"用容器 Runner"**，而不是把它放在 15.9 当"推荐项"。因为它顺带解决了开发机问题：Windows 上装了 Docker 就能 `docker run` 一个 Linux 容器跑 ezctl。
   - 但要注意：方案 15.9 的 `--network host` **在 Docker Desktop（Windows/Mac）下不是真的 host 网络**。如果目标节点和 worker 不在同一网段，或者需要 worker 主动连出去的地址被 NAT 改写，行为会和 Linux 生产环境不一致。这一条要在 Phase 1 就拿一台真机验证，别等到 Phase 3。
2. **准备一个 FakeRunner**：把"不真正执行 ezctl 但走完整状态机"的模式做进 runner 接口，让状态流转、事件、日志、重试、取消、回填 kubeconfig 这些**能在 Windows 上被单测覆盖**。方案 11.1 已经提到"worker 使用 mock runner 测试阶段成功、部分失败、取消和恢复"，建议把它从"测试手段"提升为"Phase 1 的交付物"，否则 Phase 1 除了部署文档之外没有任何东西能在本机验证。

### 2.3 SQLite 撑不住"队列 + 租约 + 心跳 + 互斥"

现在唯一的数据库是 `backend/db.sqlite3`。而方案 3.2 要的是一整套并发原语：任务租约、心跳、同一集群互斥、幂等键冲突返回已有任务。

SQLite 有三个硬限制会直接卡住这套设计：

- **没有 `SELECT ... FOR UPDATE`**，Django 的 `select_for_update()` 在 SQLite 上会抛异常或退化成普通查询，租约就不可靠了；
- 写操作是**库级锁**，多 worker 抢任务时会出现 `database is locked`；
- 没有真正的行级并发，心跳更新和状态流转会互相阻塞。

建议：**在引入第二个 worker 进程之前先切 PostgreSQL**。这是个前置决策，不是 Phase 3 的优化项。请把它写进 Phase 0。

### 2.4 机器归属需要一次收敛，顺便能删掉现有的一段脏逻辑

现在 `Machine.cluster_name` 是**字符串**（存部署名称，`k8s_machine/models.py`），角色则在 `Machine.roles`。方案 6.1 引入了 `K8sDeploymentNode`（带快照），但没说两者的关系。建议明确：

- **`K8sDeploymentNode` 是权威绑定**：有外键、有角色快照、有历史可复盘；
- **`Machine.cluster_name` / `roles` 退化成投影**：只表达"当前归属"，便于机器列表展示，由部署任务和现有的 assign/unassign 同步。

这样做还有一个附带好处：现在向导里改部署名称会触发一段 debounce 同步去改机器表（`K8sClusterDeployPage.vue` 里 `syncClusterName` / `renameTimer`，本次改动还额外加了一条"名称校验不过就不同步"的保护）。引入 slug 之后如果定为 **slug 不可变、display_name 可改**，改名就完全不需要动机器表了——**这段 debounce 同步逻辑可以整段删掉**，连带它带来的脏数据问题一起消失。建议把这条写进方案，它同时简化了 6.1 的 slug 设计和 5.2 的名称映射规则。

### 2.5 `cleanup` / `destroy` 的边界要写死

方案 6.5 说"清理前展示将影响的 IP、systemd 服务、`/etc/kubernetes`、etcd 数据目录和容器数据目录"。补充三点：

1. `ezctl destroy` 会按 **inventory 里写的节点**执行，inventory 写错就会清到别的机器上。所以 cleanup **只能使用任务快照里的节点清单**，并且执行前要**重新校验这些 IP 当前是否仍绑定这个集群**（防 IP 回收后被重新分配给别的业务，结果被误清）。
2. `rollback_required` 状态下**禁止绕过诊断包直接 cleanup**，必须先能看到失败现场。
3. Phase 1 是否就要做 destroy 需要你先定（见第 4 节）。我倾向 **Phase 1 只做"诊断包 + 人工清理"，不做自动 destroy**——这是唯一一个操作不可逆的功能，值得单独排期和单独验收。

### 2.6 幂等键的生成时机和作用域

方案写"同组织 `idempotency_key` 唯一"，但没说 key 谁生成、什么时候生成。建议补：

- key 由前端**在打开确认弹窗时生成一次并在整个提交流程中复用**，而不是每次点击都新生成。这样"用户双击"和"网络重试"两种情况天然幂等。
- 后端在 key 冲突时**返回已存在的任务**（200 + 任务详情），而不是返回 409。前端拿到就当成功跳进度页。双实现（前端生成 + 后端返回已有）比只做 409 更平滑。

### 2.7 事件表与日志表不要双写

方案 6.1 同时定义了 `K8sDeploymentEvent`（供 SSE/WS 重放）和 `K8sDeploymentLog`。Ansible 输出轻松上万行，如果每行都同时在两张表各写一份，写放大和存储都会很难看。建议明确分工：

- `K8sDeploymentEvent`：**低频**，只放阶段、进度、状态变更、错误码。这是前端时间线和进度条的数据源。
- `K8sDeploymentLog`：**高频**，放 stdout/stderr 原始行。
- 前端两条通道分开拉：时间线轮询 events，日志面板按需分页拉 logs 并且默认只 tail 最后 N 行。

同时给 events 轮询加 `limit` 上限，否则任务跑到一半前端一次请求拉几千条。

### 2.8 重试要给出"哪些阶段可以重试"的白名单

方案 6.5 给了"允许显式选择 `from_phase`"的口子，风险偏大：kubeasz 的各阶段幂等性不一样。方案 15.13 自己也说了"若 02.etcd 失败，任务停在 etcd，不能直接跳到 master"，说明作者心里有这个约束，但没落到状态机上。

建议在状态机里用**允许重试的起始阶段白名单**表达，而不是允许任意 `from_phase`。大致分三档（具体以 kubeasz 实测为准）：`render` / `precheck` 类可任意重放；`network` / `addon` 相对安全；`etcd` / `master` 属于高风险，要么禁止自动重试、要么必须人工确认。把"哪个阶段能重试"做成一张可审阅的表，比一个自由参数安全得多。

### 2.9 制品的"撤销"语义

15.4 写了撤销版本时标记 `revoked` 而不删对象，这是对的。补充两点：

- `index.json` 本身也要**签名 + 短 TTL 缓存**，否则攻击面在索引这一层；
- 一个已经创建的任务，如果它的 release 中途被撤销，应当**失败并明确告知**，而不是自动回退到另一个版本。方案没写这条。

### 2.10 可观测性别把 Phase 1 撑爆

方案第 10 章列了一整套指标（成功率、阶段耗时、SSH 失败率、节点 Ready 率）。但仓库里没有 Prometheus 指标导出的基础设施（`k8s_observability` 是对**被管理集群**的观测，不是对平台自身的度量）。

建议：Phase 1 用 `AuditLog` + `K8sDeploymentLog` + 任务表本身就够"可查"了，指标导出放到 Phase 3 跟 Redis/KMS 一起。否则 Phase 1 的范围会从"跑通一个 AIO"膨胀成"顺带搭一套监控"。

### 2.11 顺带可复用的东西

- `paramiko` 已经在依赖里，`ops/services/system_tools.py` 里已经有一套"SSH 登录校验 + 缺失主机密钥策略"的实现。方案 6.2 的 `PreflightService` 做 SSH 检查时可以直接复用这套，不用另起一套连接逻辑。
- 现有的 `TestConnection`-类的"检测结果 + 时间 + 消息"落库模式（`Machine.last_test_message` / `last_tested_at`）已经是预检结果展示的现成形状，预检结果建议用同样的形状存，前端展示也统一。

## 3. 建议调整落地顺序

### Phase 0 补充（这三个决定后面的形状，必须先做）

- **Linux 执行环境选型**：容器 Runner 还是原生 Ansible。顺手验证 Docker Desktop 下 `--network host` 能不能满足目标节点连通的场景。
- **数据库选型**：是否切 PostgreSQL。不切，就不要做多 worker。
- **SSH 认证方式**：密码临时私钥 / sshpass / 只支持预置密钥。定了才能写配置生成器。

### Phase 1 补充

- `FakeRunner` + 状态机/事件/重试/取消的完整单测，**不依赖真机也能跑**。这是 Windows 开发机上唯一能验证的交付物，优先级不低于部署本身。
- 权限码与别名登记 + 上线授权清单（见 1.3 / 1.4 / 1.5）。这三条漏一条，功能就等于没上线。
- 部署成功后补写 `K8sClusterHealthCheck`（见 1.10）。

### 把"OSS 制品"从 Phase 1 的硬前提降级

方案 15.16 的实施顺序把 OSS 配置扩展排在第一位。但按 1.2 的核对，这意味着 Phase 1 要**同时**啃四块新东西：OSS 客户端、manifest 签名校验、内容寻址缓存、制品发布流水线。风险太集中。

建议 Phase 1 允许一个过渡态：**管理员手工把校验好的 kubeasz 放到 worker 本机的固定路径**，先把"任务 → 预检 → 渲染 → 执行 → 回填 kubeconfig → 审计"这条主链路打通并验收；OSS 制品作为 Phase 1.5 接进来。这样前面那套状态机、事件、重试、权限、前端进度页的验证不被 OSS 的进度卡住，而且接入 OSS 时**正好用同一套下载记录和缓存模型做回归**。

## 4. 需要你先拍板的问题

1. **数据库切 PostgreSQL 吗？** 不切就必须放弃多 worker + 租约心跳，任务只能单进程串行跑。这一条会明显改变 3.2 和 6.1 的设计。
2. **Phase 1 可以接受"手工放置 kubeasz 制品"这个过渡态吗？** 可以的话 OSS 整体后移，Phase 1 的风险小很多。
3. **SSH 认证本阶段只支持密码，还是要连私钥一起做？** 私钥需要给 `Machine` 加字段（现在没有），属于模型改造。
4. **实时日志先轮询，还是 Phase 1 就上 Redis + WebSocket？** 我倾向先轮询（理由见 1.1），但要你确认能接受"进度页是 1~2 秒粒度刷新"而不是逐行滚动。
5. **Phase 1 要不要做自动 destroy/cleanup？** 我倾向不做，只出诊断包 + 人工清理。
6. **`K8sCluster` 状态枚举要不要加 `failed` 档？** 任务失败了集群在列表里显示成什么，需要一个明确答案（现在只有六个状态，没有"部署失败"这一档）。
7. **`page.k8s.deploy.view` 是否就作为部署任务的权限入口？** 如果是，0070 那个迁移要补一套 `PermissionMenuAction`；如果你希望部署任务单独一个页面码（便于把"看部署向导"和"操作部署任务"分开授权），那要新建页面节点并决定它的 path/aliases。
