# k8s.txt 第四轮评审

> 评审对象：`k8s.txt`（335 行，已吸收 `k8s2.txt`、`k8s3.txt` 的评审意见）。
> 文档性质：评审意见，不写代码、不修改 `k8s.txt`。
> 本轮视角：前两轮查的是「规划缺什么」，本轮 `k8s.txt` 的范围已从「新建集群」扩到 **7 类任务**（AIO / HA / add-master / add-worker / upgrade / backup / restore），因此这一轮改为核对三件事：**① 与 kubeasz 实际能力的核对 ② 规划自身的逻辑自洽 ③ 新增的备份/恢复/升级专项**。

## 评审前已核对的事实

| 事实 | 结论 | 证据 |
|---|---|---|
| kubeasz 的 `add-nodes` 命令 | **不存在**，只有单数 `add-node <cluster> <ip>` | ezctl 官方帮助：Cluster ops 段只有 `add-etcd` / `add-master` / `add-node` 与对应的 `del-*` |
| apiserver 端口的配置位置 | **`SECURE_PORT`，在 `hosts` 的 `[all:vars]`**，不在 `config.yml` | kubeasz 配置文档 |
| 证书有效期变量 | `CA_EXPIRY`（默认 `876000h` = 100 年）、`CERT_EXPIRY`（默认 `438000h` = 50 年），**在 config.yml 的 deploy 段，值是时长字符串** | 同上 |
| containerd 数据目录变量 | `CONTAINERD_STORAGE_DIR`、`CONTAINERD_ROOT_DIR`（config.yml 的 runtime 段），另有 kubelet 的 `KUBELET_ROOT_DIR` | 同上 |
| `ezctl restore` 的默认行为 | **只恢复本地最近一次 `snapshot.db`**，要恢复到指定版本需改 `roles/cluster-restore/defaults/main.yml` | 同上 |
| `ezctl backup` 的产物 | 仅 etcd snapshot，**不含 PV/业务数据**；文件落在 `/etc/kubeasz/clusters/<集群名>/backup/` | 同上 |
| 上游对大版本升级的态度 | **明确不推荐**：次版本（1.25.0→1.25.4）支持；大版本（1.24.x→1.25.x）风险高，建议新建集群并迁移 | 同上 |
| 仓库里的密钥体系 | **只有两套，且根都是 `SECRET_KEY`**：kubeconfig 用 `SHA-256(SECRET_KEY)` 派生的 Fernet；SM4 未配置时回退 `SECRET_KEY`。**没有任何 AES-256-GCM 或独立主密钥实现** | `backend/k8s_cluster/crypto.py:11-14`、`backend/backend/settings.py:6-8` |
| `SECRET_KEY` 的默认值 | **`'platform-template-local-dev-secret-change-me'`**（硬编码占位符） | `backend/backend/settings.py:6` |

## 一、与 kubeasz 实际能力不符（有上游证据）

### 1.1 `add-nodes` 这个命令不存在，9.4 的关键决策建立在它之上

**k8s.txt 原文（9.4）：** 「新增 worker 是独立任务类型 `add_worker`，支持一次选择一个或多个节点，但在 SQLite 单 Worker 下按节点顺序串行调用 `ezctl add-node <cluster> <ip>`（**多节点命令 `add-nodes` 仅在后续验证幂等性后启用**）。」

**问题：** kubeasz 的 ezctl **没有 `add-nodes` 这个命令**。官方帮助里 Cluster ops 段只有 `add-etcd` / `add-master` / `add-node`，全部是单数、一次一个 IP。9.4 整段的「多节点批量」设计（一次选多个节点、未来启用 `add-nodes`）是建立在一个不存在的命令上的。

**影响：** 前端如果按「支持一次选择一个或多个节点」来做多选，后端只能串行循环调 `add-node`。那「多选」的收益只剩 UI 便利，而 9.4 说的「任一节点失败时停止后续节点，不自动回滚已成功节点」意味着多选会让用户面对「选 5 个、成 3 个、剩 2 个怎么办」的状态，而单节点提交时这个问题不存在。

**建议：** 二选一，并写进文档：

- **方案 A（推荐）**：9.4 明确「一期只支持单节点提交，一次任务添加一个 worker」，前端不做多选。彻底消除歧义，也贴合 SQLite 单 Worker 串行。多节点需求由用户重复提交任务满足。
- **方案 B**：保留多选，但明确写成「平台串行循环调用 `add-node`，不是 kubeasz 的批量命令」，并给出失败中断后已成功节点的处理方式（推荐：写清楚「已成功的保留，失败节点可单独重试」，不要引入半成品的一致性逻辑）。

无论选哪个，都请删掉 `add-nodes` 这个不存在的命令名。

### 1.2 7.2 的字段对照表漏了 4 个字段，其中 3 个的映射与 kubeasz 实际不符

7.2 的表是「任务快照为执行依据」这条原则的落地依据，但逐项核对表单（`front/src/views/workbench/k8s/deploy/types/deploy.ts:30-55`，23 个字段）后，表里**缺 4 个字段**，且已有的几项映射在 kubeasz 里对不上。

**（1）`cniPlugin` 完全缺失 —— 后果最严重**

9.1 说「安装 CNI」，4.3 说 release 同时含 Calico 和 Flannel/Flannel CNI，**必须由用户选一个**。但对照表里没有 `cniPlugin`。快照缺这个字段，`06.network` 阶段无从确定装哪个；而 9.6 备份第 2 步又要求导出「插件清单」——不知道从哪来。

**（2）`metricsServer` 完全缺失**

9.1 说「安装 …Metrics」，但开关没进快照。与 4.3 的 Helm 语义（已明确定义）相比，Metrics 的开关语义反而丢了。

**（3）`apiServerPort` 的映射写错了位置和名字**

对照表写 `api_server_port`、标注「是否进入 kubeasz 配置 = 是」。但 kubeasz 的变量名是 **`SECURE_PORT`**，而且它在 **`hosts` 的 `[all:vars]` 段，不在 `config.yml`**。如果实现者按 `api_server_port` 这个名字去 `config.yml` 里找，kubeasz 会**静默使用默认 6443**——而 8.3 的预检又是按用户填写的端口去检查的，于是出现「预检通过、实际部署在 6443」的错位。用户以为改了端口，实际没改，且没有任何报错。

**（4）`customCertValidity` + `certValidityDays` 缺失，且取值语义与 kubeasz 冲突**

对照表完全没有这两个字段。它们的实际问题比「漏列」更麻烦：

- kubeasz 是**两个**变量：`CA_EXPIRY`（根证书，默认 `876000h` = **100 年**）与 `CERT_EXPIRY`（组件证书，默认 `438000h` = **50 年**），值是**时长字符串**。
- 而表单只有**一个**输入框，文案是「集群证书**与根证书**的有效天数」（`DeployStepAdvancedConfig.vue:124`、`141-142`），也就是一个值要同时写进两个变量。
- 表单的取值范围是 **1~3650 天**（`types/deploy.ts:115`），**最大 10 年，远小于 kubeasz 的默认值**。也就是说：用户勾选「自定义证书有效期」，无论填什么，都是在**大幅缩短**证书寿命（根证书从 100 年砍到最多 10 年）。用户的心理预期多半是「延长」，实际是缩短——这是一个必然发生误解的 UX 陷阱。
- 表单还提示「仅 Kubernetes 1.31+ 支持」（`DeployStepAdvancedConfig.vue:127`），说明这个能力本身有版本门槛。8.1 已经按 containerd 2.x 做了版本分支，但**没有覆盖这个变量的版本差异**。

**（5）`dataDir` 一个字段要影响至少三个变量，未说明**

对照表写 `data_dir_enabled`、`data_dir`，「是否进入 kubeasz 配置 = 是」。但 kubeasz 侧至少涉及：`CONTAINERD_STORAGE_DIR`、`CONTAINERD_ROOT_DIR`（config.yml 的 runtime 段）、`KUBELET_ROOT_DIR`，etcd 还有自己的数据目录变量。表单的说明是「容器与 etcd 数据统一落在系统盘」，即一个字段要同时改 containerd 和 etcd——**具体改哪几个变量、是否全部一起改，文档没有定义**。

**关联问题：** 8.3 的预检阈值写的是「etcd/control-plane 根盘至少 40GB」。如果用户把 `dataDir` 指到了独立数据盘，预检应当检查**数据盘**而非根盘。阈值表没有反映「自定义 dataDir 时检查哪块盘」，会导致预检检查了错误的磁盘。

**建议：** 7.2 补全这 4 个字段，并且对每一个「进入 kubeasz 配置」的字段**增加一列写出具体的 kubeasz 变量名与所在文件**（`hosts` 还是 `config.yml`）。这一列不加，实现者只能靠猜，而猜错的后果是静默不生效。同时：

- 证书有效期建议改成「关闭时用 kubeasz 默认；开启时最小可填 3650 天」，或把上限提高到覆盖默认值，并在 UI 上明说「当前 kubeasz 默认为根证书 100 年 / 组件证书 50 年，自定义将覆盖该默认值」。
- 明确 `CA_EXPIRY` 与 `CERT_EXPIRY` 是同一个值还是分别取值。

### 1.3 9.2 的 HA 阶段顺序与 9.1 及 kubeasz 实际顺序不一致

**k8s.txt 原文：**

- 9.1（AIO）：「依次执行 prepare、etcd、**runtime**、master、node、network、addons」
- 9.2（HA）：「依次执行 prepare、etcd、control-plane、worker、**runtime**、CNI、CoreDNS/…」

**问题：** kubeasz 的分步安装是固定的 `01.prepare → 02.etcd → 03.runtime → 04.kube-master → 05.kube-node → 06.network → 07.addons`，**runtime 在 03，永远在 control-plane/node 之前**。9.2 把 runtime 排到了 worker 之后，与 9.1 自相矛盾，也与 kubeasz 的实际顺序不符。

**影响：** 这不只是笔误。如果按 9.2 的顺序实现，HA 集群会在没有容器运行时的前提下尝试起 control-plane。而 7.2 的阶段列表（`resolve_artifacts → preflight → render → 01.prepare → 02.etcd → 03.runtime → 04.kube-master → 05.kube-node → 06.network → 07.addons → health_check → finalize`）是对的——所以是 9.2 单独写错了。建议以 7.2 为准统一 9.2。

### 1.4 9.7 的恢复流程漏了「指定备份版本」这一步，ezctl 默认只恢复本地最近一次

**k8s.txt 原文（9.7）：** 「用户必须选择 OSS 中的备份 ID」，随后「执行 `ezctl restore <cluster>`（目标 release 的 `95.restore.yml`）」。

**问题：** `ezctl restore <cluster>` **默认恢复的是本地 `backup/` 目录下的 `snapshot.db`（最近一次）**，要恢复到指定版本，需要在 `roles/cluster-restore/defaults/main.yml` 里配置目标备份。也就是说，平台选了某个历史备份 ID 之后，**必须额外做一步「把该备份放到约定位置 + 覆盖 role 的默认值」**，否则 `ezctl restore` 恢复的是上一次的备份而不是用户选的那个。

**这是数据安全的红线场景**：用户以为自己恢复到备份 A，实际恢复到备份 B，而且恢复过程会停掉整个集群。文档必须把这一步显式写进 9.7 的流程，并在恢复后校验（例如对比恢复出的 etcd 版本、或者恢复前的 snapshot 校验和）。

## 二、逻辑死锁与自相矛盾

### 2.1 【最严重】9.7 的「应急备份」在灾难恢复场景下必然失败，导致恢复永远无法执行

**k8s.txt 原文（9.7）：** 「恢复是破坏性任务类型 `restore`…**恢复前自动生成当前集群的应急备份（若失败则禁止继续）**。」

**问题：** 这是一个逻辑死锁。恢复的真实使用场景恰恰是**集群已经不可用**（etcd 数据损坏、控制平面崩溃、误操作删了对象）。而「应急备份」要执行 `ezctl backup`，它需要集群的 etcd 还在正常服务。于是：

> 集群挂了 → 需要恢复 → 但恢复要求先备份当前状态 → 备份因为集群挂了而失败 → 禁止继续 → **恢复永远执行不了**。

也就是说，这条规则在最需要它的场景下**百分之百阻止救援**，只在集群还健康时（此时通常也不急着恢复）才能通过。

**建议：** 把硬阻断改成**有条件的、带审计的**流程：

1. 恢复任务开始时先**探测集群健康度**（API Server 可达 + etcd 健康）。
2. **集群健康** → 强制应急备份，失败则禁止继续（保留现有语义，这是对的）。
3. **集群不健康** → 允许用户**显式跳过**应急备份，但必须：二次确认、手动输入 `display_name`、确认文案里明确写「集群当前不可用，跳过应急备份，恢复后当前状态不可回退」，并记录到审计。
4. 无论是否跳过，都要求用户确认「已了解当前集群状态无法保留」。

这条不改，9.7 设计的恢复能力在实际事故中是用不上的。

### 2.2 跨版本恢复无解：9.7 要校验兼容性，9.5 又禁止降级

**k8s.txt 原文：** 9.7「校验备份源 Kubernetes/kubeasz 版本与当前集群兼容性」；9.5「禁止跨越未支持版本、**降级**或运行时切换」。

**问题：** `ezctl restore` 恢复的是 **etcd 数据**，它不会改变节点上的二进制版本。所以：

- 若备份来自 1.35、当前集群已升级到 1.36 → 恢复后是「1.35 的 etcd 数据 + 1.36 的 kube-apiserver/kubelet」。这是**不受支持的组合**，且没有办法通过「恢复」本身修正（要修正就得降级二进制，而 9.5 禁止降级）。
- 若备份与当前版本一致 → 没有这个问题。

于是「兼容性校验」的规则实际上只有两种可能的结果，文档必须选一个并写清楚：

- **规则 A（推荐）**：**只允许恢复到与当前集群 Kubernetes + kubeasz 版本完全一致的备份**。跨版本恢复明确不支持，错误提示为「备份来自 1.35，当前集群为 1.36，跨版本恢复不支持；如需回到 1.35，请新建集群后迁移」。
- **规则 B**：允许跨版本恢复，但必须说明恢复后如何把二进制对齐（= 需要先降级，与 9.5 冲突，需要同时放宽 9.5）。

**在规则未定的情况下，9.7 的「校验兼容性」是一句无法实现的描述。** 另外请一并说明：9.5 的升级流程**是否要求升级前必须能恢复到升级前的版本**（这是升级安全网的核心），如果是，那升级前的那份备份必须与「升级后版本」形成可恢复链路——这在规则 A 下不成立（升级后就不能恢复到旧备份了）。这个矛盾需要在「升级」和「恢复」两节之间对齐。

### 2.3 备份的价值依赖 kubeasz release 的生存期，而 release 可以被撤销、缓存会被清理

**k8s.txt 原文：** 5.3「release 被撤销后，新任务直接失败」；5.4「只清理未被活动任务引用且超过 30 天的缓存，不删除 OSS 原对象」；9.7「用备份中的 inventory/config 和**对应 OSS release** 重建 kubeasz 工作区」。

**问题：** 恢复需要「对应 OSS release」的制品（kubeasz 源码、二进制、镜像），但：

- 5.3 允许 release 被撤销，撤销后**新任务直接失败**——恢复任务算不算「新任务」？按字面算是，那就永远无法恢复。
- 5.4 的缓存清理基于「未被活动任务引用」，而备份是**历史引用**，不会被任何活动任务引用，所以缓存必然被清掉——恢复时要重新从 OSS 拉。
- 更根本的是：**备份的保存期（30 天）与 release 的生存期没有任何绑定关系**。管理员完全可以撤销 1.33 的 release，而 60 天前基于 1.33 做的备份还在，此时那份备份已经**无法恢复**——备份本身成了废纸，却没有任何告警。

**建议（三选一或组合）：**

- **方案 A（推荐）**：备份时把「恢复所需的最小制品集」一并存入备份归档——至少包含该集群的 `inventory`/`config.yml`（9.6 已做）+ 该 release 的 `manifest.json` + kubeasz 源码包。这样即使 release 被撤销，备份仍可自洽恢复。代价是备份包变大（kubeasz 源码几十 MB）。
- **方案 B**：规定「被任何未过期备份引用的 release 不得撤销」，撤销前必须检查引用，并在撤销流程里给出「有 N 个备份依赖此 release」的提示。
- **方案 C**：恢复允许从「已撤销的 release」拉取制品（即撤销只影响**新建**，不影响恢复），并在 5.3 里写明这个例外。

无论选哪个，请在文档里明确「备份的可用性边界」，否则用户会以为「有备份 = 能恢复」。

### 2.4 6.1「快照不可变」与 9.3/9.4 的扩容必然冲突

**k8s.txt 原文：** 6.1「新增 `K8sDeploymentNode` 保存机器 ID、IP、角色和认证快照；**执行期间禁止读取变化后的 Machine 角色**」；9.3「成功后更新 `K8sDeploymentNode` 和集群节点投影」；9.4「执行后检查节点加入」。

**问题：** 9.4 说新增 worker 成功后会「更新 `K8sDeploymentNode`」，也就是说**快照是可变的**——这与 6.1 的「快照」语义（不可变、执行期间不读变化）冲突。更实际的困惑是：**扩容之后，后续任务读哪一份配置？**

具体场景：集群 A 初始 1 个 master，后经 9.3 加了 2 个 master 变成 3 个。此时：

- 9.5 的升级要用「原始配置快照」（9.3 说 Worker 使用「该集群已保存的 kubeasz 版本、**原始配置快照**」）——那是 1 个 master 的版本还是 3 个的？
- 如果用了 1 个 master 的快照去升级，kubeasz 的 `hosts` 会缺 2 个 control-plane，**升级可能把另外两个 master 漏掉**，或者让集群处于不一致状态。
- 9.6 的备份声称导出「节点清单」，导的是哪个？

**建议：** 明确区分两种「快照」：

- **任务快照**（`K8sDeploymentNode`）：属于单个任务，任务结束即固定，用于回放和审计——**永远不变**。
- **集群当前配置**（`hosts` + `config.yml`）：属于集群，会随扩容/升级变化，每个任务开始时以「执行时的集群配置」为准，并在任务成功后被新版本覆盖。

也就是：9.3/9.5 的「原始配置快照」应改为「**集群当前的生效配置**」，它不是只读的历史快照，而是随扩容更新的、有版本的集群状态。建议给 `K8sCluster` 或一个专门的「集群配置版本」记录当前 `hosts`/`config.yml` 的内容与版本号，扩容/升级成功即追加新版本。这样升级、备份、恢复都有明确的「读哪一版」的答案。

### 2.5 7.3 的超时只「标记 failed」，没有终止已经在跑的 Ansible

**k8s.txt 原文（7.3）：** 「单阶段默认超时 2 小时、整任务默认 8 小时，**超时标记 failed 并保留诊断**。」

**问题：** 「标记 failed」是**改数据库状态**，「终止 Ansible」是**杀进程**，文档只说了前者。如果只改状态不杀进程：Ansible 会继续跑完剩余阶段，期间还可能继续修改目标节点；跑完后如果代码里有回写状态的逻辑，又可能把已经标记为 failed 的任务改回别的状态，或者写入事件污染状态机。

**建议：** 明确超时的处理动作是「标记 failed + 向进程组发送信号终止 + 保留已产出的诊断」。与 8.2 已经写好的「取消时 Worker 以独立 POSIX 进程组启动 Ansible，向进程组发送信号」复用同一套机制即可，只是触发源从「用户取消」变成「超时」。

顺带一个容量问题：单任务超时 8 小时 + 单 Worker 串行，意味着一个卡住的任务会让**后面所有任务排队等 8 小时**。建议补充：进度页能否显示「队列位置 / 前面还有 N 个任务」，否则用户只能看到 `queued` 一直不变。

### 2.6 备份保留策略的两条规则互相冲突

**k8s.txt 原文（9.6）：** 「备份保留策略默认 **30 天**、每集群**至少保留最近 3 个成功备份**」。

**问题：** 两条规则冲突时以哪个为准？一个集群 60 天没做备份，只剩 2 个成功备份（都已超 30 天）——是删掉它们（遵守 30 天）还是保留（遵守至少 3 个）？

**建议：** 明确优先级。推荐写成「**先满足『至少保留最近 3 个』，再按 30 天清理**」，即：一个备份只有在「超过 30 天」**且**「不是最近 3 个成功备份之一」时才可删除。这样两个规则不打架，且「至少 3 个」作为下限保护灾难场景。

## 三、密钥体系与备份安全（本轮新增的重点）

### 3.1 「平台数据安全主密钥」在仓库里不存在

**k8s.txt 原文：** 9.6「DEK 由**平台数据安全主密钥**包装，包装后的 DEK、nonce 和 key version 写入 manifest」；9.7「使用**平台数据安全主密钥**解包 DEK 并执行 AES-256-GCM 验证/解密」「平台主密钥必须纳入离线灾备；密钥缺失时禁止尝试恢复并明确报错」；12 节 Phase 0「统一 settings/SECRET_KEY」。

**已核实：** 仓库里**没有 AES-256-GCM 实现，也没有独立的「数据安全主密钥」**。现有的两套密钥都是 `SECRET_KEY` 的派生：

```python
# backend/k8s_cluster/crypto.py:11-14   （kubeconfig 加密）
def _fernet():
    digest = hashlib.sha256(settings.SECRET_KEY.encode('utf-8')).digest()
    return Fernet(base64.urlsafe_b64encode(digest))
```

```python
# backend/backend/settings.py:6-8       （SM4 主密钥）
SECRET_KEY = os.getenv('DJANGO_SECRET_KEY', 'platform-template-local-dev-secret-change-me')
_sm4_key_source = os.getenv('SM4_MASTER_KEYS') or os.getenv('SM4_MASTER_KEY') or SECRET_KEY
SM4_MASTER_KEYS = [key.strip() for key in _sm4_key_source.split(',') if key.strip()]
```

所以 9.6/9.7 引入的「主密钥 + DEK 包装 + key version + 离线灾备」是**这个平台目前完全没有的基础设施**，属于新增的核心安全依赖，而 12 节 Phase 0 把它简化成了「统一 settings/SECRET_KEY」——那是**不成立的**，`SECRET_KEY` 和「可离线灾备的主密钥」是两件事（见 3.3）。

**建议：** 在 9.6 之前增加一节「数据安全主密钥」，明确：主密钥的来源（环境变量名？文件？KMS？）、长度与格式、如何生成、存放位置、备份方式、轮换流程、丢失后的影响面。这是备份功能能否成立的前提，不能只在 Phase 0 用一句「统一 settings/SECRET_KEY」带过。

### 3.2 `SECRET_KEY` 的默认值是硬编码占位符，且会静默回退——与 9.7「密钥缺失即报错」的意图相反

**已核实：** `backend/backend/settings.py:6`：

```python
SECRET_KEY = os.getenv('DJANGO_SECRET_KEY', 'platform-template-local-dev-secret-change-me')
```

**问题：** 这是一个**公开的、写在源码里的默认值**。如果生产部署忘了设 `DJANGO_SECRET_KEY` 环境变量：

- kubeconfig 的 Fernet 密钥 = `SHA-256("platform-template-local-dev-secret-change-me")`——**任何拿到源码的人都能算出来**，等于 kubeconfig 未加密。
- SM4 主密钥同样回退到这个值（`settings.py:7`），平台设置里的 OSS AccessKey、LLM Key 一并失效。
- 如果 9.6 的备份加密也沿用这条链路，那么备份包里的 **etcd snapshot、集群 CA、kubeconfig 全部等同于明文**。

而 9.7 说「密钥缺失时禁止尝试恢复并明确报错」——**实际行为是「密钥缺失时静默使用公开默认值」，不会报错**。这与设计意图完全相反。

**建议（两条都要做）：**

1. 备份任务创建前增加一次**主密钥健康检查**：确认密钥来自显式配置（非默认值）、长度满足要求；不满足则**拒绝创建备份任务**并明确报错，而不是降级加密。
2. 把 `settings.py:6` 的默认值改成「非 DEBUG 环境下未显式配置即启动失败」，或在启动时打印显著告警。当前这个默认值在开发期方便，但在生产是个静默的安全漏洞。

### 3.3 三套密钥同根于 `SECRET_KEY`，轮换即所有历史备份永久作废

**问题：** 平台现在（及 9.6 之后）会有三套密码学用途，但**根都是 `SECRET_KEY`**：

| 用途 | 实现 | 密钥来源 |
|---|---|---|
| 平台设置敏感字段（OSS/LLM Key） | SM4 | `SM4_MASTER_KEYS`，未配置时回退 `SECRET_KEY` |
| kubeconfig | Fernet | `SHA-256(SECRET_KEY)` |
| 备份包（9.6 新增） | AES-256-GCM | 拟用「平台数据安全主密钥」 |

**后果：** `SECRET_KEY` 一旦轮换（安全事件、人员变动、合规要求），三样数据同时失效——包括**所有历史备份**。而 9.7 要求「平台主密钥必须纳入离线灾备」，说明设计者已经意识到主密钥的极端重要性，却没有把「主密钥 == `SECRET_KEY`（或其派生）」这个事实写明。

**建议：** 明确二选一：

- **方案 A（推荐）**：备份加密使用**独立于 `SECRET_KEY` 的主密钥**，这样 `SECRET_KEY` 轮换不会摧毁历史备份。同时说明「kubeconfig 与平台设置字段在 `SECRET_KEY` 轮换后需要重新录入」这一既有影响。
- **方案 B**：承认 `SECRET_KEY` 就是最高机密，在 9.6/12 节明确「`SECRET_KEY` 的离线灾备与备份包同等重要，丢失即所有备份与 kubeconfig 永久不可恢复」。

另外 9.6 的 `K8sClusterBackup` 已经记录了 `key version`，这是为轮换准备的——但轮换需要**同时保留旧密钥**才能解密旧备份，这一点在 12 节 Phase 3 的「制品签名轮换」里提了签名，**没有提数据密钥轮换**。建议一并补上。

### 3.4 备份的 `backup-manifest.json` 自身没有完整性保护

**k8s.txt 原文（9.6）：** manifest 包含「cluster slug、备份 ID、创建时间、源版本、文件清单、密文大小、密文 SHA-256、加密算法和 schema 版本」；5.3 明确「一期不引入签名」。

**问题：** 密文有 SHA-256 校验，但**存放这个 SHA-256 的 manifest 本身是明文且没有保护**。任何能改 OSS 对象的人（例如凭据泄露）可以同时替换 `backup.tar.zst.enc` 和 manifest 里的哈希，校验就会通过。9.6 第 5 步的「回读校验」只能防传输损坏，防不了这个。

**建议：** 既然 5.3 已经决定一期不签名，那就在 9.6 里**写明这个残留风险**，并至少做一件事来降低影响：把 `backup-manifest.json` **放进加密包内部**（而不是作为同级明文对象），外层只留一个最小的、由不可篡改信息构成的文件（如「备份 ID + 密文 SHA-256」）。这样攻击者改 manifest 就需要先破解加密包。

### 3.5 「集群证书/CA 元数据」措辞含糊，且证书并不在平台机上

**k8s.txt 原文（9.6 第 2 步）：** 「导出任务快照、inventory、`config.yml`、节点角色、Kubernetes/kubeasz 版本、插件清单、制品 manifest 哈希、**集群证书/CA 元数据**和 kubeconfig」。

**两个问题：**

1. **「证书/CA 元数据」到底含不含 CA 私钥？** CA 证书（公钥）随集群分发给任何客户端，敏感度低；**CA 私钥**能签发任意集群身份，是最高敏感物。措辞含糊会让实现者自行决定，而两种选择的备份安全等级完全不同。请明确写出包含的具体文件清单。
2. **这些证书不在平台机上。** kubeasz 把集群证书生成在**控制节点的 `/etc/kubernetes/ssl/`**，`ezctl backup` 只产出 etcd snapshot。所以 9.6 第 2 步的这些内容需要**平台主动 SSH 到 master 节点抓取**——这一步在流程里没有体现，而它决定了备份任务需要额外的 SSH 权限、额外的失败点（master 不可达时备份是否算失败）、以及额外的脱敏要求。

**建议：** 把第 2 步拆成「平台本地可得」与「需 SSH 从控制节点抓取」两组，逐项列出文件名与来源路径，并明确 CA 私钥是否包含。

### 3.6 平台已有 Velero 备份接口，9.6 没有说明两者的关系

**已核实：** `backend/k8s_platform/services.py:364-399` 已经实现了 `list_velero_backups` / `create_velero_backup` / `create_velero_restore`，直接操作 Velero CRD；`k8s_platform/services.py:63` 还有 Velero 的能力探测。

而 9.6 设计了一套**全新**的集群备份体系（`ezctl backup` → etcd snapshot → AES-256-GCM 加密包 → OSS）。9.6 的末句提了「备份不包含业务应用持久卷数据；应用数据需使用 **Velero**/存储快照等独立方案」——**说明设计者知道 Velero 的存在**，但没有说明「平台已经有一份 Velero 接口」，也没说明两者如何分工。

**问题：** 读者（以及后续实现者）很容易误以为要为新体系重复建设一套备份管理，或者反过来，以为 9.6 的备份能覆盖 Velero 的场景。

**建议：** 在 9.6 开头用一小段划清边界：

| 层级 | 内容 | 实现 |
|---|---|---|
| 集群级（本规划范围） | etcd snapshot、集群证书/配置、kubeasz 制品引用 | `ezctl backup` + OSS 加密包，9.6 新增 |
| 应用级（不在本规划范围） | K8s 资源、PV 数据 | **复用既有的 `k8s_platform` Velero 接口**，不重复建设 |

并明确「集群级备份不能替代应用级备份，反之亦然；恢复整集群时必须先做集群级恢复，再用 Velero 恢复应用」。

### 3.7 `K8sClusterHealthCheck` 是追加型历史表，「更新 HealthCheck」的措辞与实际模型不符

**已核实：** `K8sClusterHealthCheck`（`backend/k8s_cluster/models.py:92-105`）**没有唯一约束**，`cluster` 是普通外键（`related_name='health_checks'`），每次检测由 `K8sCluster.mark_test_result` 追加一条新记录（`models.py:62-69`），列表接口是只读分页（`k8s_cluster/views.py:260-265`）——即**历史流水表**。每集群的「最新状态」另有冗余字段 `last_test_status/last_test_message/last_tested_at`（`models.py:38-40`）。

**问题：** 9.5 说「升级完成后更新集群版本、制品引用、kubeconfig 元数据和 **HealthCheck**」——HealthCheck 只能**新增一条**，不能「更新」。措辞应改为「新增一条健康检查记录」。

**顺带一个设计缺口：** 该表没有关联部署任务的字段（无 `deployment_id`）。9.1/9.2/9.3/9.5 都说「创建 HealthCheck」，但如果运维排查时需要回答「这条健康检查是哪次任务产生的」，现有模型答不上来。建议在新增 `K8sDeployment` 时，给 HealthCheck 增加一个可空的 `deployment` 外键（或在 `detail` JSON 里固定写入任务 ID），成本很低但排查价值高。

## 四、kubeasz 集成的路径模型缺失

### 4.1 8.1 说「渲染 `clusters/<slug>/hosts`、`config.yml`」，但基线模板从哪来、AIO 与 HA 用哪份，都没写

**问题：** kubeasz 的 `hosts` 和 `config.yml` 都是**几百行的模板文件**，且随 kubeasz 版本变化。「渲染」有两种完全不同的做法：

- **整文件重写**：为每个 kubeasz 版本维护完整模板 → 上游一升级就要重做，**必然漏掉新增变量**，且新增变量的默认值会与上游不一致。
- **基线 + 覆盖**（推荐，也是 kubeasz 自己的做法）：以 kubeasz 源码 `example/` 下的模板为基线，只覆盖平台需要控制的那些键。

而 `example/` 下**至少有两套 hosts 基线**（单机 all-in-one 与多节点 multi-node），9.1 的 AIO 和 9.2 的 HA 应当用**不同的基线**。文档只写了一句「渲染 `hosts`」，没有区分。

**建议：** 8.1 明确写成：

1. 基线来自任务所用 kubeasz 版本的 `example/` 模板（AIO 与 HA 分别指定）；
2. 平台只覆盖 7.2 对照表中标注「进入 kubeasz 配置」的那些键，其余保持基线默认；
3. 记录「基线模板的哈希 + 覆盖的键值」作为配置哈希的一部分，便于审计与版本对比；
4. 当 kubeasz 版本变化导致基线新增键时，不做特殊处理（继承上游默认），但要在测试验收里加一条「升级 kubeasz 版本后重新对比生成结果」。

### 4.2 kubeasz 源码目录与任务工作区的关系没有定义

**问题：** 涉及三处路径，但它们的包含关系没有说清：

- 7.3「run 工作区 `/var/lib/k8smanager/runs/<deployment-id>`」
- 5.4「缓存 `/var/lib/k8smanager/artifacts/<sha256>`」
- 8.1「`clusters/<slug>/hosts`、`config.yml`」

而 kubeasz 的实际约束是：`ezctl` 是 kubeasz 源码根目录下的脚本，它通过**自身位置**推导 BASEDIR，然后读写 `<BASEDIR>/clusters/<集群名>/`。官方文档里这个目录是 `/etc/kubeasz/clusters/<集群名>/`。所以必须回答：

- **kubeasz 源码解压在哪？** 每个任务解压一份到 `<run-dir>/`，还是全局共享一份？
- **`clusters/<slug>/` 在哪个路径下？** 是 `<run-dir>/kubeasz/clusters/<slug>/` 吗？
- 9.3 说「Worker 使用该集群已保存的 kubeasz 版本、原始配置快照」——**「已保存」保存在哪**？数据库的哪个字段，还是某个持久目录？9.5 又说「通过任务隔离工作区的目标 kubeasz 源码、`config.yml` 和版本变量传入」——听起来是要重建，但重建的源是数据库快照还是别的地方？

**建议：** 在 7.1 或 8.1 补一张路径表：`缓存目录`、`任务工作区`、`kubeasz 源码目录`、`clusters/<slug>` 目录、`诊断包输出目录`，并明确「源码每任务一份（隔离，代价是磁盘与解压耗时）」还是「全局共享（省空间，代价是 `clusters/` 下会堆积所有集群、且与任务隔离矛盾）」。从 9.5 的措辞看设计者倾向「每任务一份」，那就明确写出来，并说明磁盘开销的估算。

### 4.3 `ezctl checkout` 会修改全局 `~/.kube/config`

**问题：** `ezctl checkout <cluster>` 的作用是「切换默认 kubeconfig」，它会写平台机的 `~/.kube/config`。这是一个**全局可变状态**。k8s.txt 的 9.1~9.7 没有提到它，但 9.7 的健康检查、9.3 的节点检查都需要操作 kubeconfig。

**风险：** 单 Worker 串行时不会并发冲突，但会出现「上一个任务 checkout 到集群 A，本次任务忘了 checkout 到集群 B，于是 kubectl 打到了 A 集群」这种**跨集群误操作**——对恢复/升级这类破坏性操作是致命的。

**建议：** 明确规定 Worker 对 kubeconfig 一律使用**显式 `--kubeconfig <工作区路径>`**，不依赖 `~/.kube/config` 的默认上下文；并在预检或任务开始时校验「当前 kubeconfig 指向的集群 == 目标任务集群」。这条看似细节，但能避免最危险的一类事故。

### 4.4 `ezdown` 被放进每个 release，但它在部署侧不应该被执行

**k8s.txt 原文：** 5.2 的目录结构里每个 release 都有 `commands/ezdown`；5.3 的发布流程是「解析对应 ezdown → 下载…」。

**问题：** `ezdown` 是**联网下载器**（从互联网拉镜像和二进制），它的用途在**发布侧**——`sync_kubeasz_artifacts.py` 通过解析它来知道要下载什么。而在**部署侧**，所有制品都已经从 OSS 下好了，跑 `ezdown` 会去连互联网，这与 8.1「禁止目标节点访问 OSS」的离线原则、以及 2.1 的「从自有 OSS 获取制品」直接冲突。

**建议：** 明确写「部署侧只使用 `ezctl`；`ezdown` 仅作为发布侧解析来源保留在 release 中，部署 Worker 不得执行」。如果保留它是为了完整性，加一句说明就够了；但如果实现者误调用，会静默产生对公网的依赖。

## 五、升级专项

### 5.1 上游明确不推荐大版本升级，而 9.5 的升级范围覆盖跨大版本

**k8s.txt 原文（9.5）：** 「升级是独立任务类型 `upgrade`，只能从当前支持版本升级到配置中心已启用且 kubeasz 有对应 release 的目标版本；禁止跨越未支持版本、降级或运行时切换。」

**上游的明确立场：** kubeasz 官方文档对升级的说明是——**次版本升级**（如 1.25.0 → 1.25.4）完全支持、风险低；**大版本升级**（如 1.24.x → 1.25.x）**不推荐、风险高，建议部署新集群并迁移工作负载**。

**问题：** 4.1 的矩阵是 1.33/1.34/1.35/1.36，对应的 kubeasz 是 3.6.7/3.6.8/3.6.10/3.7.0。也就是说：

- **Kubernetes 侧**每个都是一个大版本（1.33→1.34 就是大版本升级）；
- **kubeasz 侧** 3.6.x → 3.7.0 也是跨大版本。

按上游口径，4.1 矩阵里**任何一次跨版本升级都属于「不推荐」的类别**。而 9.5 的表述把它当成常规能力，只在最后说「控制平面阶段失败进入 `rollback_required`，不自动降级」。

**建议：** 明确降级预期，二选一：

- **方案 A**：9.5 限定为「只支持同一 Kubernetes 次版本内的补丁升级」（如 1.36.0 → 1.36.2），跨次版本升级引导用户「新建集群 + 迁移工作负载」。这与上游口径一致，风险最低。
- **方案 B**：保留跨版本升级，但必须：① 在文档和 UI 上标注「上游不推荐，属于高风险操作」；② 升级前强制备份 + 强制输入 `display_name` 确认；③ 明确「失败即 `rollback_required`，且**平台不提供自动降级**，需要人工按诊断包处理」。9.5 目前只做到了第 ③ 条的一半。

无论选哪个，Phase 3 把 `upgrade` 排到最后是对的——但**理由应该写明是「上游不推荐、风险高」，而不只是排期问题**。

### 5.2 缺少版本偏差（skew）规则

**问题：** Kubernetes 有明确的版本偏差策略：kubelet 最多可以比 kube-apiserver 落后 3 个次版本；kube-proxy、kubectl 各有更严的限制。如果 9.5 允许「从 1.33 升到 1.36」，正好跨 3 个次版本，处在 kubelet 偏差的边界；而如果集群里还有 1.32 的节点，就**越界**了。

文档完全没有提到 skew 规则。

**建议：** 在 9.5 的升级预检里明确增加一条「版本偏差检查」：源版本与目标版本跨越的次版本数 ≤ 2（保守取值），且集群内所有节点版本一致；不满足则拒绝创建升级任务，并给出「请先升级到中间版本」的提示。这条在跨版本升级开放的方案 B 下是必须的。

## 六、约束的执行机制

### 6.1 「单 Worker」这个前提只靠文档纪律维持，没有技术强制

**k8s.txt 原文：** 7.3「SQLite 是唯一允许使用的数据库……部署服务固定为单 Worker、单任务串行执行……**不实现多 Worker**」；12 节 Phase 0「部署服务以 systemd 管理单个 Worker，**禁止启动第二个 Worker 实例**」。

**问题：** 整个 SQLite 方案的根基是「同一时刻只有一个 Worker」。但这个前提**没有任何技术手段保证**——没有行锁、没有租约（7.3 明确不实现）、没有数据库层的唯一约束，只有一句「禁止启动第二个 Worker」。运维误操作（systemd 配了 `Restart=always` 又手工起了一个、或从两个终端起了两次）就会破坏这个前提，导致**两个 Ansible 同时操作集群**——这是最危险的并发形态，而且在 SQLite 无锁的情况下不会有任何报错。

**建议：** 用最低成本的方式把它变成硬约束，三选一：

- Worker 启动时获取一个**文件锁**（`/var/lib/k8smanager/worker.lock`，`flock`），拿不到就直接退出并打印「已有 Worker 在运行」。
- 写一个 PID 文件，启动时检查 PID 是否存活。
- 在 SQLite 里放一条「Worker 实例」记录（含启动时间、PID、心跳），启动时做原子更新。

三种都能在几行内实现，但能把「靠纪律」变成「靠机制」。既然 7.3 已经明确「不能通过增加 Worker 绕过本约束」，那就应该让这个约束真的无法被绕过。

### 6.2 「集群详情页」在代码里不存在，10 节的入口没有落脚点

**k8s.txt 原文（10 节）：** 「在**集群详情页**新增『添加 Master』『添加 Node』『集群升级』『立即备份』『备份记录/恢复』入口」。

**已核实：** 全仓库 grep `ClusterDetail|集群详情` 在 `front/src` 下 **0 命中**，前端没有 `/k8s/clusters/:id` 这样的详情路由；后端也没有对应的页面码——集群接入的页面码是 **`page.k8s.clusters.view`（复数）**，name=`集群接入`，path=`/k8s/clusters`（`ops/migrations/0067_k8s_permission_menu.py:6`），**不存在** `page.k8s.cluster.view` 或任何「集群详情」页面码。

所以 10 节和 9.3~9.7 规划的五类运维入口，**当前没有任何页面可以承载**。这不是笔误，而是一块需要先决定的地基：

- **方案 A**：新建「集群详情」页面码（如 `page.k8s.cluster_detail.view`），并配套前端路由与菜单登记。好处是语义清晰、可以和「集群接入」列表页的权限分开（能看列表 ≠ 能进详情做运维）。
- **方案 B**：复用 `page.k8s.clusters.view`，把这些入口做成集群列表页的行内操作或展开面板，不引入新页面码。好处是改动最小，坏处是「集群接入」这个页面同时承担了查看和运维两类职责，权限颗粒度粗。

无论选哪个，都要在文档里写明，因为它同时决定了 6.3 的操作码挂在哪个页面节点下。

**另外，前端入口必须按 `origin` 区分：** 6.2 明确「接入型和部署型在列表展示和可用操作上分开」，那么「添加 Master / 集群升级 / 备份 / 恢复」这些入口对 `origin=imported` 的集群**必须全部隐藏或禁用**——否则用户会对一个从阿里云接进来的集群点「集群升级」。10 节只写了「新增入口」，没有写这个区分。

### 6.3 【机制性障碍】7.4 设计的 `page.k8s.deploy.backup/restore/add_master/upgrade` 永远不会被检查

这条是本轮最具体的技术发现，因为它不是「设计不够好」，而是「按现在的写法实现出来不生效」。

**k8s.txt 原文（7.4）：** 「创建、重试、取消、cleanup、**add-master**、**add-worker**、**upgrade**、**backup**、**restore** 分别使用独立操作码（如 `page.k8s.deploy.add_master`、`page.k8s.deploy.backup`、`page.k8s.deploy.restore`）。在 `ops/permissions.py` 的 `API_PAGE_ALIASES` 登记 `/k8s/deployments` **及集群运维 API**。」

**已核实的机制：**

1. **页面码解析顺序**（`ops/permissions.py:129-132`）：先查 `API_PAGE_ALIASES`（静态前缀表，**最长前缀优先**，匹配规则是 `path == prefix or path.startswith(prefix + '/')`），**命中即返回**；只有全部未命中时才回落到数据库菜单的 `page_code_for_path`。
2. **现有别名表里已有 `/k8s/clusters` → `page.k8s.clusters.view`**（`permissions.py:22`）。
3. **操作码 = 页面码去掉 `.view` + `.{动作}`**，由 `permission_catalog.py:276-280` 的 `action_code()` 拼接；动作必须通过 `PermissionMenuAction.page` 外键挂在对应页面节点下（`ops/models.py:263-284`）。

**推出的结论：** 7.4 规划的集群运维 API 是 `/api/v1/k8s/clusters/<cluster_id>/backups/`、`.../upgrade/`、`.../nodes/add-master/`（7.4 的路由清单）。归一化后是 `/k8s/clusters/<id>/backups`。按第 1、2 条：

> `/k8s/clusters/<id>/backups` 会被别名表里的 `/k8s/clusters` **前缀命中**，解析为 **`page.k8s.clusters.view`** —— 而不是 `page.k8s.deploy.*`。

于是 `page.k8s.deploy.backup`、`page.k8s.deploy.restore`、`page.k8s.deploy.add_master`、`page.k8s.deploy.upgrade` 这些码**从头到尾不会被任何请求命中**：它们挂在 `page.k8s.deploy` 节点下，而所有运维请求都被解析成 `page.k8s.clusters.view`。两个后果：

- **权限形同虚设**：任何拥有「集群接入」查看权限的人，都能调用备份、恢复、升级接口（恢复是破坏性操作）。
- **或者反过来**，如果实现者为了「让权限生效」而把动作名硬编码到视图上，就会出现「页面码是 `page.k8s.clusters`、动作码却是 `page.k8s.deploy.backup`」——`action_code()` 的拼接规则是「页面码 + 动作」，两者对不上，校验依然失败。

**还有一个附带问题：** `API_PAGE_ALIASES` 是**静态前缀表**，写不了 `<cluster_id>` 这样的动态段。所以「登记集群运维 API」这件事，对带参数的路由**做不到**——只能登记到 `/k8s/clusters` 这一层（已被占用），或者依赖数据库菜单 path 的 `:param` 支持（`permission_catalog.py:211-218` 的 `_path_matches` 支持 `:param` 正则），但后者只在别名表未命中时才生效，而这里别名表**已经命中了**。

**建议（两条路，推荐第一条）：**

- **方案 A（顺应现有机制）**：把集群运维操作码**挂到 `page.k8s.clusters` 页面节点下**，即 `page.k8s.clusters.backup`、`page.k8s.clusters.restore`、`page.k8s.clusters.add_master`、`page.k8s.clusters.add_worker`、`page.k8s.clusters.upgrade`。这与 API 路径前缀天然的解析结果一致，改动量最小，且权限语义上更准确——它们是「集群接入」这个资源上的运维动作。部署向导相关的（create / retry / cancel / dry-run）才留在 `page.k8s.deploy.*`。
- **方案 B（另起前缀）**：把运维 API 迁到独立前缀下（例如 `/api/v1/k8s/cluster-ops/<id>/...`），在别名表登记 `/k8s/cluster-ops` → 新页面码。前缀干净、不与 `/k8s/clusters` 冲突，但要改 API 设计。

顺带一个**当前就存在**的同类问题：`page.k8s.deploy.view` 的 path 是 `/k8s/clusters/deploy`（`0070_k8s_cluster_deploy_page.py:7`），而 `/k8s/clusters/deploy` 同样会被别名表的 `/k8s/clusters` 前缀命中，解析为 `page.k8s.clusters.view`——**数据库里那个页面节点的 path 实际上不会起作用**。目前 `/k8s/deploy-options` 有显式别名指向 `page.k8s.deploy.view`（`permissions.py:21`）才让这个码能被用到。建议一并复核这条链路，确认部署向导页的权限判定是不是真的走的 `page.k8s.deploy.view`。

**这条值得在 7.4 里写清楚「新增页面/接口时必须同步登记 `API_PAGE_ALIASES`，且要注意前缀冲突」——否则很容易上线一个永远返回 403 或永远放行的接口。**

## 七、文档一致性

### 7.1 「一期」与「Phase 1」不是同一个概念，容易误读交付范围

**问题：** 2.1 的标题是「**一期**范围」，其中包含了「新增 Master、添加 worker Node、版本升级」和「集群状态备份到 OSS，以及从 OSS 下载校验后恢复/回滚」。而 12 节的阶段划分是：

- Phase 1：AIO 闭环（+ 备份模型）
- Phase 2：HA 与串行运维（add-master / add-worker / backup / restore）
- Phase 3：扩展（upgrade）

也就是说 2.1 的「一期」实际跨越了 Phase 1、2、3。读者看到「一期范围」会以为这些都在第一个交付里。

**建议：** 把 2.1 的「一期范围」改成「**整体范围（全部阶段）**」，或者按阶段拆分标注（「Phase 1：AIO」…）。这是纯措辞问题，但影响交付预期。

### 7.2 7.2 对照表的「是/否」需要增加「具体变量名」一列

这一点在 1.2 已经详述。这里只强调必要性：7.2 的表目前只能回答「这个字段重不重要」，不能回答「这个字段写进哪个文件的哪个变量」。而 16 节把「任务快照为执行依据」定为不可变原则，意味着这张表是实现时的唯一依据——它必须精确到变量名，否则原则落不了地。

## 九、本轮未覆盖与顺带提示

### 未覆盖

- 备份/恢复在 OSS 上的具体目录权限、生命周期规则（OSS 侧的 bucket policy）
- `K8sClusterBackup` 的完整表结构设计（本轮只核对了密钥、命令与既有模型层面）
- 恢复/升级的并发锁：7.3 的单 Worker 串行已隐含覆盖，但「同一集群不允许两个任务」是否需要显式约束（例如队列里同时排着 upgrade 和 backup）尚未讨论
- 前端的具体交互细节（高风险确认弹窗的文案与流程）

### 顺带提示：2.2「不使用 Redis」与仓库现状的关系

2.2 写「不使用 Redis 或其它数据库；进度使用 HTTP 轮询」。核实后的仓库实际情况是：

- Django Channels **已经全链路接线**：`settings.py:31`（`INSTALLED_APPS` 含 `channels`）、`settings.py:72`（`ASGI_APPLICATION`）、`asgi.py:14-15` 注册了两条 WebSocket 路由；
- channel layer 是 `InMemoryChannelLayer`（`settings.py:74-78`，硬编码、无环境变量覆盖）；
- 前端确实在用：`K8sPodTerminal.vue`（Pod 终端 exec）与 `K8sLogPage.vue`（Pod 日志）都建了 WebSocket 连接。

**这不是矛盾**（2.2 说的是「新增的部署进度不引入 Redis / 不引入 WebSocket」，而且 Pod exec/logs 是「一个连接绑一个 consumer」的场景，`InMemoryChannelLayer` 够用）。但建议在 2.2 补一句「现有 Pod 终端与日志的 WebSocket 保持现状，不在本次范围内调整」，避免读者误以为要拆掉既有 WebSocket，或者误以为新增的部署进度可以顺带复用这套机制——**部署进度是 Worker 进程产生的，与 Web 进程跨进程，`InMemoryChannelLayer` 在跨进程场景下不生效**，这正是 2.2 选择 HTTP 轮询的原因，值得写明。
